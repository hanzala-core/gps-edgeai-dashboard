GPS-EdgeAI Software Development Plan
Draft v0.4 · 18 November 2026 · GPS-EdgeAI semester dashboard

1. Goal and current position
Build a local web dashboard that lets a student or demonstrator run a simulated GPS receiver session,
inspect its readings and status, and reopen saved session data. The semester demo must show a working
flow from browser to backend to database and back. The receiver research project provides the longer-term
requirements for recorded and live data.
The GitHub repository and local checkout currently have main with the README and Git setup files. No
open GitHub issues or additional remote branches were visible when reviewed. The submitted SRS is
Version 1.0, Draft 1, dated 20 October 2026. This plan selects a semester subset and ties it to the SRS
requirement IDs.

3. Proposed design
Use Next.js (App Router, React, and TypeScript) with SQLite for processed records. One Next.js application
supplies the page rendering, browser interactions, and all server-side data access; there is no separate
Python service, API route layer, or client-side fetch code. SQLite remains the storage engine because D-05
and §7.2 require documented persistence; the app reaches it from server code. Keep the interface plain and
functional, using shadcn/ui primitives where they help and avoiding decorative styling. The submitted SRS
describes a host dashboard and allows CSV or JSON session files. Section 7.2 requires a documented schema
and retention policy when a database is added.

Status of valid, unavailable, or stale. Include available position, velocity,

Per-satellite entries with PRN, tracking status, available C/N₀ in dB-Hz, Doppler

corresponding entries.

events

A time and message for session changes, errors, and simulated anomaly events.

Keep AI classification per satellite. A session-wide count summarizes those classes. Display PVT status
and AI quality as separate fields. The first sample can contain one tracked satellite and an unavailable PVT
value, so every team member can implement and verify the same case.

Storage and server functions
Start with sessions and readings linked by session ID. Document the schema with column names,
types, units, keys, and how long demo records are retained. For the first iteration, keep the satellite array
with its reading. Add a separate satellite table later if per-satellite queries require it. Store events separately
when session and alert logging is added. Keep the local database file out of version control and keep
schema initialization in the application setup.

All data access runs on the Next.js server. Server Components read SQLite directly when rendering the
dashboard. Mutations are Server Actions in files marked with the "use server" directive; buttons and forms
call them directly. Do not add route handlers, API folders, or client-side fetch calls.
Proposed server function

Purpose

The first save action can create a demo session on demand. Later, session controls supply the active
session ID. Agree on the returned values and error messages before dashboard integration. Everything runs
on the same local Next.js server, so the whole build starts with one command (pnpm dev).

5. How to verify the demo
1. Start the local Next.js app with pnpm dev and confirm the dashboard loads.
2. Open the dashboard and check that Simulation Mode is visible. Save a demo reading and confirm its

values appear in history.
3. Restart the app and reopen the session. Check that the same saved ID, observation time, and values are

present.
4. Start and stop a simulated session. Check its state and times, and confirm the reading count stays

steady after Stop.
5. Run a scenario with an unavailable or stale fix and another with an anomalous satellite. Check labels,

counts, and saved events.
6. Ask a teammate to run the same demo from the documented setup and record the result against each

requirement ID.
The first slice is done after check 3. The semester release is ready after checks 1-6. Record a short
demonstration after the team passes the checklist.

6. Receiver integration after the semester slice
The original SRS describes GPS L1 C/A reception, FPGA I/Q streaming, acquisition and tracking,
navigation decoding and PVT, and per-channel quality classification. Treat each as a module with a
defined input and output. The relevant sequence is FR-01-FR-03 for sample reception, FR-04-FR-09 for
acquisition/tracking, FR-10-FR-14 for navigation/PVT, FR-15-FR-19 for classification, and FR-20-FR-22
for the dashboard, evaluation, and sessions.
1. Recorded data. The local SoftGNSS settings point to Static_5mins.bin. Check the recording

metadata and produce a verified output, then map available navigation and tracking fields into the
common reading format. Mark missing fields unavailable and document their units and time source.
2. Live source. Agree on the FPGA transport, sample packing and rate, channel order, start/stop

behavior, and buffer status before writing the adapter. Keep raw capture files with their capture
configuration and store processed summaries by session.
3. Edge AI and evaluation. Agree on the eight SRS tracking features, labelled examples, validation data,

and evaluation metrics. Show genuine classification outputs with the applicable source and validity.
Measure receiver and model performance before reporting that an SRS target was met.
